# Session notes — 2026-10-20

This is a summary of the working session that built this skill, from the first idea to v0.3.1. Use it to remember why things are the way they are.

## Goal

Make game UI design with Claude give high-quality results every time, instead of "one-prompt slop". The aim is a general skill for any project. The output is mockups plus all the information needed to build the UI. The user decides screens, platform, and references each time the skill runs.

## The core idea

Slop comes from a missing process and missing constraints, not from a missing prompt. With no brief, no references, and no system, the model fills every gap with the statistical average: dark glass, cyan glow, generic fonts.

So the skill has three parts:

1. **A fixed process with approval gates.** Brief, references, information architecture, design system, directions, screens, critique, handoff. Motion is optional, after the static layout is approved.
2. **Explicit structure that can be checked.** Tokens, components, addresses, a registry, and a validator.
3. **Critique against a rubric before delivery.** Two anti-slop checks: rubric check 9 (identity) and M5 (motion identity). Each one asks: name the specific choice that ties this screen to this game.

## Decisions, in order

| # | Decision | Why |
|---|---|---|
| 1 | Process skill with phases and approval gates | Stops generic first drafts. Each phase is cheap to fix before the next one builds on it. |
| 2 | General skill; screens, platform, and references are chosen per run | The user's choice. |
| 3 | Reference research offer (Phase 1b): references, image-model prompts, or skip | Strong references are the main source of taste. |
| 4 | Image-model prompts are for mood only, never layout. Prompts describe materials and real objects, not "game UI" | The words "game UI" pull image models back to the generic average. Layout must come from shipped games and Phase 2. |
| 5 | Addressing system: layers `$` token, `@` component, screen paths; `#tags`; selectors; edit commands | Without addresses, "make the bar thinner" is ambiguous (one instance, the component, or the token?), and the ambiguity causes drift. |
| 6 | IDs name the role, not the look (`health-bar`, not `red-bar`) | A style change must not break addresses. |
| 7 | Fixed tag set; new tags need approval | Free tags grow into chaos. |
| 8 | Three or more similar overrides lead to a proposed new variant | Stops silent drift from the system. |
| 9 | Registry as JSON (`ui-registry.json`) | A script can read it. Markdown tables cannot be validated reliably. |
| 10 | Validator script, 0 errors before delivery | Claude keeping the registry by hand drifts in long sessions. |
| 11 | Inspector overlay inside every mockup | Point at elements instead of describing them. It exports edit commands. |
| 12 | Motion as an optional phase (5b), offered after static approval | Motion work on an unapproved layout is wasted. |
| 13 | Tools live in `scripts/`, not inside SKILL.md | Clean diffs, testable code, one copy. Claude copies the files and does not retype them. |
| 14 | Inspector picks elements by geometry, not browser hit testing | The real bug: HUD layers with `pointer-events: none` and full-screen overlays made every click select the root. Common in game mockups. |
| 15 | Selector field and Move panel button | User request, plus the panel covered the bottom-right HUD corner at 1080p and larger. |
| 16 | Adopt knowledge from omer-metin's `game-ui-design` skill as pattern cards, rewritten, numbers checked | Their skill is knowledge without process; this one is process without enough knowledge. They complement each other. |
| 17 | Every number marked [std] (published) or [heur] (starting point) | Avoids presenting guesses as standards. |
| 18 | Text floor from XAG 101: console 26 px, PC 18 px at 1080p | Replaced an unsourced "28 px" and their 14–18 px, which fails on TV. |
| 19 | HUD visibility states (hidden, peek, persistent, expanded) with triggers | A HUD that shows everything all the time is a strong slop sign. |
| 20 | Input map with actions, `@prompt` components, no hard-coded "Press A" | One action, one button on every screen. Prompts follow device and rebinding. |
| 21 | Background test in the inspector (bright, mid-gray, dark, busy) | Makes "readable over gameplay" testable instead of a rule only. |
| 22 | Navigation cost check: presses and depth per task, against frequency budgets | Reachable is not enough. Common features must be cheap to reach. |
| 23 | Severity: over a default budget = WARN; over a user-set budget = ERROR; no path = ERROR | User's rule. Default budgets are guesses; the user's own budgets are commitments. |
| 24 | Navigation graph as SVG, offered once, with an auto-update option | User request. Generated from the registry, so the picture cannot drift from the data. |
| 25 | References come from the user (screenshots, URLs, notes); Claude reads only the pages sent | User's choice: do not appear to take from curated collections. Browsing them directly gives the curators their visits. |
| 26 | Distribution: Git repo as the single source; Claude Code marketplace; ZIP from GitHub Releases for claude.ai | Personal claude.ai plans have no sharing or sync, so a ZIP is needed. The release workflow builds it from a tag, so every ZIP has a version. |

## Rejected, and why

- **A persona ("you have shipped AAA titles")** from the other skill: it adds no information and makes the model sound more certain than it should.
- **"Correct the user using the references"**: the references have no sources, and some numbers were wrong.
- **Their regex lint rules**: written for app CSS and Unity code, and they give many false alarms on mockups. For example, every 24 px icon would count as a small touch target, the 1920 px stage as a fixed size, and the inspector's own z-index as an error. Replaced by token-level checks.
- **Generated images for layout**: layout must come from Phase 2 and real games.
- **A separate motion skill**: it would duplicate the registry and the addressing system.
- **Graphviz for the graph**: it would need an install on claude.ai. The simple built-in layout is enough for 10–20 screens.

## Known limits

- The hard-coded prompt check reads English only. 「Aボタンで開く」 is not caught.
- The handheld text floor uses the console value. XAG 101 does not cover handheld PCs.
- Navigation cost counts first visits with a gamepad only. Mouse cost and "remember last focus" are not modeled. Task frequencies are guesses until playtest data exists.
- Navigation budgets are heuristics. No published standard was found.
- The graph layout gets crossing lines in large, highly connected menus. A link shared by several tasks shows the worst status of those tasks.
- Motion prototypes show intent and timing, not engine behavior.
- Icons and art are placeholders. Claude does not make final art.
- A web page URL gives Claude only text, not images. Screenshots work much better as references.
- The CI step that installs Claude Code to validate manifests is untested on GitHub. If it needs sign-in, remove that step.
